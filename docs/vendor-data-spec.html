ICU 生命徵象與神經評估　資料格式說明

本院端由整合引擎定時取得資料，轉換後以 HTTP POST 送至貴司系統。 本文說明送出的 JSON 結構、欄位定義與必須注意的重送與去重行為。

01

共通約定

兩種資料共用以下規則。

項目約定
編碼 UTF-8（含中文標籤，如「昏迷指數」）
Content-Type application/json; charset=utf-8
最外層結構 永遠是 JSON 陣列。即使只有一位病人也是長度 1 的陣列，沒有資料則是 []。
時間格式 "YYYY-MM-DD HH:mm:ss"，例如 "2026-08-04 11:24:05"。
字串本身不帶時區標記，一律為台灣時間（UTC+8）。不是 ISO 8601，沒有 T 與 Z。
空值 以 null 表示，不會用空字串。欄位一定存在，不會整個消失。
排序 依床號自然排序（ICU-2 在 ICU-10 之前），沒有床號者排最後。
資料量 生命徵象單批約 3 MB（未壓縮），每 5 分鐘一批，量體穩定； 神經評估目前遠小於此，每小時一批，但會隨評估項目增加而成長（見下方「後續擴充」）。 可視貴司需求以 gzip 壓縮送出（約可降至 200 KB，見 §6 Q4）。
後續擴充 生命徵象的量測項目已固定，後續不會增加。
神經評估的評估項目則會持續納入新的類別，項目清單是開放式的。因此請以下列方式實作：
  • 忽略未知欄位，不要因為出現沒看過的欄位就整批拒收。
  • 不要假設神經評估 records[] 的項目種類固定， 新的 terseLabel 與 interventionId 會隨時出現。
  • 已定義欄位的名稱與型別不會變動，只會新增。
分組單位 一筆＝一位病人（或一床），其量測／紀錄收在 records[] 陣列中，不重複外層欄位。
02

資料一：生命徵象

Vital Signs

每 5 分鐘一批
頻率
每 5 分鐘
涵蓋範圍
該次送出前約 5–6 分鐘
分組
一床一筆
單批大小
約 3 MB（未壓縮）

範例

// 最外層是陣列，一床一筆
[
  {
    "bed": "ICU-01",
    "lifetimeNumber": "A123456",
    "records": [
      {
        "terseLabel": "ABP",
        "propName": "systolic",
        "numericValue": 118,
        "measurementTime": "2026-08-04 11:24:00",
        "storeTime": "2026-08-04 11:24:05"
      },
      {
        "terseLabel": "ABP",
        "propName": "diastolic",
        "numericValue": 62,
        "measurementTime": "2026-08-04 11:24:00",
        "storeTime": "2026-08-04 11:24:05"
      },
      {
        "terseLabel": "HR",
        "propName": null,
        "numericValue": 78,
        "measurementTime": "2026-08-04 11:24:00",
        "storeTime": "2026-08-04 11:24:03"
      }
    ]
  }
]

外層欄位

欄位型別可為 null說明
bed string 否 床號，例如 ICU-01。分組的鍵。
lifetimeNumber string 是 病歷號。以床號對應病人資料而得；對應系統暫時無法查詢時為 null（見 §5）。
records array 否 該床於本批時間範圍內的量測值，至少一筆。

records[] 欄位

欄位型別可為 null說明
terseLabel string 是 量測項目，例如 HR、ABP、SpO2、CVP。
propName string 是 細項，例如 systolic、diastolic、mean。單值項目（如 HR）為 null。
numericValue number 是 量測數值，可能含小數。單位由項目本身決定，不另外附帶單位欄位。
measurementTime string 否 儀器量測到的時間。臨床上以此為準。
storeTime string 否 寫入資料庫的時間，通常略晚於 measurementTime 數秒。

識別一個量測項目要用 terseLabel + propName 兩欄。 單看 ABP 無法分辨是收縮壓、舒張壓還是平均動脈壓。

已降頻。監視器可能每幾秒送出一次，本院端已先篩選為「每床、每分鐘、每項目最新一筆」， 不會送出秒級的原始資料。

只包含目前有病人的床。空床與測試中的儀器不會出現在資料裡。

03

資料二：神經評估

Neuro Assessment

每 60 分鐘一批
頻率
每 60 分鐘
涵蓋範圍
該次送出前約 60–65 分鐘
分組
一位病人一筆
項目清單
開放式，將持續擴充

範例

[
  {
    "lifetimeNumber": "A123456",
    "bed": "ICU-01",
    "records": [
      {
        "interventionId": "3F2504E0-4F89-11D3-9A0C-0305E82C3301",
        "terseLabel": "昏迷指數",
        "terseForm": "E4V5M6",
        "storeTime": "2026-08-04 11:24:05",
        "addTime": "2026-08-04 11:24:00",
        "chartTime": "2026-08-04 11:20:00"
      }
    ]
  }
]

外層欄位

欄位型別可為 null說明
lifetimeNumber string 是 病歷號。
bed string 是 床號。
records array 否 該病人於本批時間範圍內有異動的評估紀錄。

records[] 欄位

欄位型別可為 null說明
interventionId string (GUID) 否 評估項目的識別碼，大寫 GUID。同一項目在所有病人身上是同一個值。
terseLabel string 是 項目名稱，例如「昏迷指數」、「RASS」、「體溫」。中文，UTF-8。
terseForm string 是 實際填寫的值，例如 E4V5M6。是文字不是數字，格式依項目而異。
chartTime string 是 臨床上這筆紀錄所代表的時間。顯示與判讀請以此為準。
addTime string 是 紀錄建立時間。
storeTime string 否 寫入資料庫的時間。本院端以此判斷「這段期間有異動」。

評估項目是開放清單，請勿寫死。目前的項目（昏迷指數、RASS、體溫…）只是起點， 後續會持續納入新的評估類別，terseLabel 與 interventionId 都會出現沒看過的值。

建議以 interventionId 為主鍵維護一張可由設定調整的對照表； 遇到未知項目請保留原始值並記錄，不要丟棄整筆或整批。需要對照表時本院端可隨時提供最新清單。

這不是在床病人清單。只有在該時段內「有新增或修改紀錄」的病人才會出現。 某位病人這一小時沒有新的神經評估，就不會在這批資料裡——這不代表他出院或沒有病歷。

因此請勿以本資料判斷病人是否在床，也不要以「未出現」推論任何臨床狀態。

04

重複資料與去重

本院端會刻意送出重疊的資料，去重責任在接收端。 以下說明重複的來源，並提供唯一鍵的建議供貴司實作參考。

來源一：重送。若某一批 POST 失敗，本院端會整批重送，該批內容與前次完全相同。

來源二：批次邊界。每一批的時間範圍是「查詢當下往回推 5 分鐘」， 並非接續上一批的結束點。排程若提前觸發，相鄰兩批的邊界會重疊。

來源三：紀錄修改（僅神經評估）。同一筆紀錄被修改後會再次出現， chartTime 與前次相同，storeTime 較新。

建議的唯一鍵

資料建議唯一鍵重複時的處理
生命徵象 bed + terseLabel + propName + measurementTime 視為同一筆，以新蓋舊或直接忽略皆可
神經評估 lifetimeNumber + interventionId + chartTime 同一筆若被修改後重送，storeTime 會不同而 chartTime 相同， 此時應以 storeTime 較新者為準

以上僅為建議，實際採用何種鍵值由貴司依系統設計自行決定。

05

需要預期的異常情況

以下都是正常運作下會出現的狀況，請勿視為錯誤資料而整批拒收。

情況資料上的表現建議處理
該時段確實沒有資料 整批是 [] 正常回應 2xx 即可，這不是故障
病人資料暫時查不到 lifetimeNumber 為 null，其餘欄位正常 請勿整批拒收；以床號暫存或先擱置，後續批次會補上正確病歷號
項目標籤尚未建檔 terseLabel / propName 為 null 該筆可略過，並請回報本院端補上對照
部分加護單位查詢失敗 該單位的床這批不會出現，其餘照常送出 依現有邏輯處理即可，缺漏會在下一批補回
單批資料量大 目前實測約 3 MB（未壓縮），且隨在床數浮動 這是本案最需要優先確認的限制，請見 §6 Q4
06

需要貴司回覆的事項

以下確認後，本院端即可完成轉換與送出設定。

Q1

接收端點與認證方式（正式與測試各一組）

請提供 URL、HTTP method（預設 POST）、認證方式 （API Key／Bearer Token／憑證／不需驗證），以及是否需要固定的自訂 header。

請一併提供測試用端點：本院端會先以實際資料在測試端點完成對接驗證， 確認無誤後再切換正式。兩組設定若相同請直接註明。

Q2

JSON 結構確認

請確認可接受 §2、§3 所定義的結構與欄位名稱——本院端即以此格式送出。 若有窒礙難行之處，請具體指出欄位並說明原因，再行討論。

Q3

成功與失敗如何判定

以 HTTP 狀態碼判定即可，或需檢查回應 body 中的欄位？失敗時的回應範例為何？ 這決定本院端何時觸發重送。

Q4

單次請求的大小上限、壓縮與逾時

本題請優先回覆。生命徵象單批實測約 3 MB（未壓縮，隨在床數浮動）， 每 5 分鐘一次。這已超過不少 API 的預設上限（常見的預設值為 1 MB 或 4 MB）。 需要確認兩件事：

  • body 大小上限為何，以及超過時的回應。
  • 是否接受 Content-Encoding: gzip。本資料的欄位名重複率高， 壓縮比約 14:1，3 MB 可降到約 200 KB，是最省事的解法。

另請提供建議的 timeout 秒數。

本文件為草案，欄位定義依實際程式輸出撰寫；範例中的病歷號、床號與數值均為示意。
確認後將更新版本號並附上實際取樣的資料檔。
