ICCA 中介資料庫 Schema

醫院端定時把 Philips ICCA 的資料寫進由醫院端建置與維護的中介資料庫，廠商唯讀取用。
生命徵象是即時的儀器量測（每 5 分鐘一批）；其他臨床資料為非即時的人工填寫， 同樣每 5 分鐘檢查一次，有新增或修改的紀錄就寫入、沒有就不寫，內容可能是事後補填或修改的。

權責分工

中介資料庫是醫院端的資產：2026-08-06 與資訊室主任的會議中討論確認，由醫院端提供一台專用 Server 來放這個資料庫，建置、寫入、備份、清理與保留期限都由醫院端負責， 廠商如何取用（唯讀帳號或 API）也由醫院端決定。 廠商不需要準備任何主機或資料庫。

醫院端只寫、廠商只讀，交界就是這兩張表；廠商拿不到中介資料庫以外的任何權限。 拋轉中斷時廠商會看到資料停止增加，核對方式見 §5。

01

共通約定

兩張表共用以下規則。

項目約定
資料庫 Microsoft SQL Server，跑在醫院端提供的專用 Server 上（2026-08-06 會議確認，見 §0）。 兩張表在同一個資料庫、同一個 schema（預設 dbo）。 實際的伺服器位址、執行個體與資料庫名稱隨帳號一併核發（見 §6 Q1）。
存取方式
醫院端決定		 兩種做法由醫院端擇一，欄位定義與內容相同：
  • 唯讀帳號——直接查表，只有這兩張表的 SELECT 權限。 醫院端只寫不讀，建議查詢加 WITH (NOLOCK) 避開寫入當下的鎖。
  • 醫院端提供 API——廠商不直接連資料庫。 存取控制走醫院端核發的 token，每次呼叫帶著它； 能拿到哪些資料由醫院端依 token 篩選後才回傳。
編碼 文字欄位一律 NVARCHAR（Unicode），含中文標籤如「昏迷指數」。
時間欄位 臨床時間（兩張表都叫 chartTime）型別是 DATETIME，值是台灣時間（UTC+8），不帶時區標記。
稽核時間只有一欄 insertedAt，值同樣是台灣時間（UTC+8）—— 它是資料庫伺服器蓋的 SYSDATETIME()。全表只有一種時間基準， 臨床時間與稽核時間可以直接相減。
沒有 updatedAt／changedAt：兩張表都只新增不更新（見下方「寫入節奏」）， 列寫進去之後不會被動到，這兩欄不會有值可以放。
空值 以 NULL 表示，不會用空字串。例外見 §2、§3 的鑰匙欄位說明。
寫入節奏 每 5 分鐘一輪，兩張表同時撈；該輪沒有新資料就不寫，不會產生空批次。 一批是一個交易，要嘛整批進去、要嘛整批沒有，不會讀到寫到一半的狀態。
兩張表都是「只新增、不更新、不刪除」：已經寫進去的列永遠不會被改動。 生命徵象是即時量測，來源本身就是只寫不改；臨床紀錄是非即時的人工填寫， chartTime 可能遠早於寫入時間，也可能事後被護理師修改—— 被改過的紀錄會以新的一列進來，原本那一列原封不動留著（見 §3）。
資料量 生命徵象約每批 1,800 列、每天 50 萬列上下，隨在床數浮動； 臨床紀錄目前遠小於此，但會隨納入的表單項目增加而成長（見下方「後續擴充」）。
保留期限 由醫院端排程清理，期限依廠商需要而定（見 §6 Q2）。 未確認之前不會刪除任何資料——但也請勿把本表當成長期歷史庫使用， 需要留存的資料請自行複製一份。
後續擴充 生命徵象的量測項目已固定，後續不會增加。
臨床紀錄的表單項目則會持續納入新的類別，項目清單是開放式的。因此請以下列方式實作：
  • 不要用 SELECT *，明確列出需要的欄位——新增欄位時貴司才不會受影響。
  • 不要假設 terseLabel / interventionId 的值域固定， 會隨時出現沒看過的值。
  • 已定義欄位的名稱與型別不會變動，只會新增。

結構

CREATE TABLE dbo.CDSUnvalidatedData (
  lifetimeNumber   NVARCHAR(32)  NOT NULL,   -- 唯一鍵
  terseLabel       NVARCHAR(32)  NOT NULL,   -- 唯一鍵
  propName         NVARCHAR(64)  NOT NULL,   -- 唯一鍵
  chartTime        DATETIME  NOT NULL,   -- 唯一鍵
  numericValue     FLOAT         NULL,
  textValue        NVARCHAR(256) NULL,   -- 非數值的量測值
  storeTime        DATETIME  NULL,   -- 增量讀取的水位線
  insertedAt       DATETIME  NOT NULL DEFAULT (SYSDATETIME())
  -- 上面四欄合起來是唯一鍵，四欄值都相同的資料只會有一列；
  -- 唯一性由醫院端的寫入流程保證，索引與條件約束不對外開放
);

欄位

欄位型別可為 NULL說明
lifetimeNumber nvarchar(32) 否 病歷號，唯一鍵的第一欄。查不到病歷號的量測不會寫進本表（見 §5）， 所以這一欄不會是 NULL。床號不在本表——同一床會換病人、 同一位病人也會轉床，一律以病歷號認人。
terseLabel nvarchar(32) 否 量測項目，例如 HR、ABP、SpO2、CVP。
propName nvarchar(64) 否 細項，例如 systolic、diastolic、mean。 單值項目（如 HR）是空字串 ''，不是 NULL——它是唯一鍵的一部分。
chartTime datetime 否 臨床時間：儀器量測到的那一刻（UTC+8）。臨床上以此為準，時序圖表請用這一欄。 跟 dbo.CISData 的 chartTime 是同一個角色，所以同名； 在 ICCA 來源端這一欄叫 measurementTime。
numericValue float 是 量測數值，可能含小數。單位由項目本身決定，不另設單位欄位。
textValue nvarchar(256) 是 非數值的量測值，例如儀器送出的模式、狀態或帶單位的字串。 絕大多數項目是數值，這一欄為 NULL，值在 numericValue。
兩欄請都讀。判斷一列的值要先看 numericValue，是 NULL 才看 textValue——不要假設每一列都有數值。
storeTime datetime 是 ICCA 端寫入的時間（UTC+8），通常略晚於 chartTime 數秒。 增量讀取請用這一欄當水位線，見 §4。
insertedAt datetime 否 本列寫進中介資料庫的時間（UTC+8）。跟 storeTime 的差距就是 這條管線的落後幅度，核對拋轉有沒有斷掉請用這一欄（見 §5）。 不要拿它當水位線——同一批寫入的列時間戳相同。

底色那三列是同一次血壓量測：ABP 靠 propName 分收縮／舒張／平均，所以是三列而不是一列；HR 這種單值項目的 propName 是空字串而不是 NULL。
沒有床號欄位，病人一律以 lifetimeNumber 認； 查不到病歷號的量測整列不寫入（見 §5）。
上表 textValue 全部是 NULL，因為這幾項都是數值型的量測； 非數值的項目則反過來，numericValue 是 NULL、值在 textValue。

識別一個量測項目要用 terseLabel + propName 兩欄。 單看 ABP 無法分辨是收縮壓、舒張壓還是平均動脈壓。

已降頻。監視器可能每幾秒送出一次，醫院端已先篩選為「每位病人、每分鐘、每項目最新一筆」， 表中不會有秒級的原始資料。

只包含對得到病歷號的量測。空床、測試中的儀器，以及病人對應系統暫時查不到病歷號的那一輪，都不會寫進來（見 §5）。

本表只有監視器送出的量測，不是「全部的生命徵象」。 目前的項目是 HR、SpO2、ABP、CVP、NBP、PAP、ICP、PCWP。 體溫不在這張表——它是護理師填在表單上的，寫進 dbo.CISData（見 §3）。找不到某個項目時請先查對照清單， 不要用「它是生命徵象所以應該在這裡」推論。

本表的列寫進去之後不會再變，也不會被刪除。來源的 CDS 是直接跑轉的環狀表， 只有寫入、沒有更新，所以本表沒有 isDelete 這類作廢註記，也沒有 updatedAt／changedAt。同一組唯一鍵只會有一列—— 這一點跟 dbo.CISData 不同（見 §3）。

FiO2 有三種寫法。來源表單不同，terseLabel 分別是 FiO2 %、FiO2 %.（多一個句點）與 FiO2。 用名稱比對時三個都要收。

藥物醫囑跟表單紀錄長得一樣，但來源不同。 上表最後一列不是護理師填的表單，而是鎮靜／止痛／肌肉鬆弛／升壓藥物的醫囑紀錄， 寫進同一張 dbo.CISData、欄位完全相同。這幾列的 terseLabel 是藥品醫囑名稱而不是評估項目名。目前涵蓋 11 類藥品：

Fentanyl、Precedex、Midazolam、 Fresofol、Nimbex、Dopamin、 Levophed、Epinephrine（含 Norepinephrine）、 Dobutamine、Pitressin、Perdipine

結構

CREATE TABLE dbo.CISData (
  interventionId  NVARCHAR(36)   NOT NULL,  -- 識別鍵
  chartTime       DATETIME   NOT NULL,  -- 識別鍵
  lifetimeNumber  NVARCHAR(32)   NOT NULL,
  terseLabel      NVARCHAR(32)  NULL,
  terseForm       NVARCHAR(32)   NULL,   -- 不含單位
  verboseForm     NVARCHAR(256)  NULL,   -- 含單位
  storeTime       DATETIME   NULL,   -- 增量讀取的水位線；也是版本的先後
  isDeleted       BIT          NOT NULL DEFAULT (0),
  insertedAt      DATETIME  NOT NULL DEFAULT (SYSDATETIME())
  -- 另有醫院端內部使用的病人識別欄位，與上列 interventionId、chartTime
  -- 共同構成識別鍵，不對外開放
  --
  -- 沒有主鍵：同一組識別鍵會有多列（紀錄的先後版本），見下方說明
);

欄位

欄位型別可為 NULL說明
interventionId nvarchar(36) 否 評估項目的識別碼（GUID）。比 terseLabel 穩定，對照表請以此為鍵。
chartTime datetime 否 這筆紀錄在臨床上代表的時間（UTC+8）。時序請用這一欄，不是寫入時間。
lifetimeNumber nvarchar(32) 否 病歷號。查不到病歷號的紀錄不會寫進本表（見 §5），所以不會是 NULL。
terseLabel nvarchar(32) 是 項目名稱，例如「昏迷指數」、「RASS」、「體溫」；藥物醫囑的列則是藥品醫囑名稱。尚未建檔時為 NULL。
terseForm nvarchar(32) 是 實際填寫的值，不含單位，例如 E4V5M6、37.2腋溫、-2。 是文字不是數值，要算數值請自行轉型。
verboseForm nvarchar(256) 是 同一筆填寫值的完整版本，含單位，例如 37.2腋溫、40 %。 來源沒有提供時為 NULL。
storeTime datetime 是 ICCA 端最後寫入的時間（UTC+8）。紀錄被修改時這一欄會變新， 所以同一組識別鍵底下 storeTime 最大的那一列就是現行版本。 增量讀取也用這一欄當水位線，見 §4。
isDeleted bit 否 作廢註記。0 ＝ 有效、1 ＝ 這筆在 ICCA 已經被刪除或作廢。 醫院端不會實際刪除列、也不會去改既有的列：作廢是再寫一列 同樣識別鍵、isDeleted = 1、storeTime 更新的紀錄。 因此判斷一筆現在是不是有效，要看最新那一列的 isDeleted， 不是看有沒有 isDeleted = 1 的列存在（見 §4 的範例）。
insertedAt datetime 否 本列寫進中介資料庫的時間（UTC+8）。列寫進去就不會再變，所以沒有 updatedAt。不要拿它當水位線——同一批寫入的列時間戳相同； 它是用來核對拋轉有沒有斷掉的（見 §5）。

04

怎麼只讀新的資料

兩張表都是只新增的：已經寫進去的列不會被改、也不會被刪，醫院端也不搬移資料， 所以表會一直長大。貴司若要定時同步，請用 storeTime 當水位線（watermark）。

建議寫法：生命徵象

-- @last = 上一次同步時記下的水位線（第一次跑給一個很早的時間）
SELECT lifetimeNumber, terseLabel, propName,
       numericValue, textValue, chartTime, storeTime
FROM   dbo.CDSUnvalidatedData WITH (NOLOCK)
WHERE  storeTime > @last
ORDER BY storeTime, lifetimeNumber, terseLabel, propName, chartTime;

-- 這一輪讀到的最大 storeTime 就是下一次的 @last

本表同一組唯一鍵只會有一列，讀到什麼就是什麼，不必再挑版本。

建議寫法：臨床紀錄（要現值就要挑版本）

-- 同一組識別鍵底下可能有多列（先後版本），取最新那一列
WITH inc AS (
  SELECT interventionId, chartTime, lifetimeNumber, terseLabel,
         terseForm, verboseForm, storeTime, isDeleted,
         ROW_NUMBER() OVER (
           PARTITION BY lifetimeNumber, interventionId, chartTime
           ORDER BY storeTime DESC
         ) AS rn
  FROM   dbo.CISData WITH (NOLOCK)
  WHERE  storeTime > @last
)
SELECT * FROM inc
WHERE  rn = 1               -- 這一批裡每組識別鍵只留最新的那一版
ORDER BY storeTime, interventionId, chartTime;

注意這只在「這一批」裡挑最新。如果上一批已經寫過同一組識別鍵的舊版本， 貴司自己那一份要用識別鍵 + storeTime 比較新才覆蓋的方式更新， 否則跨批次時舊版本可能蓋掉新版本。

兩張表都沒有流水號欄位。水位線一律用 storeTime，它是 ICCA 端的寫入時間： 生命徵象是儀器上傳的時間，臨床紀錄被修改時也會跟著變新，所以新資料與新版本都追得到。

為什麼不是用 chartTime。 那是臨床時間，不是寫入時間。護理師 12:05 補填 11:00 的紀錄時 chartTime 是 11:00， 以臨床時間當水位線會直接漏掉。

為什麼不是用 insertedAt。它是中介庫的寫入時間，同一批寫進來的列 時間戳完全相同，當水位線會在批次邊界重複讀或漏讀。它的用途是核對拋轉有沒有斷（見 §5）。

dbo.CISData 的作廢是「多一列」，不是改既有的列、也不是刪列。 某筆被作廢時，會出現同樣識別鍵、isDeleted = 1、storeTime 更新的一列， 原本 isDeleted = 0 的那一列留著。
所以增量查詢不要加 isDeleted = 0——那樣會讀不到「這筆被作廢了」這個變化。 請照上面的寫法整批讀進來、挑出每組識別鍵最新的那一列，再看那一列的 isDeleted 決定是更新還是作廢自己那一份。對外呈現資料時才過濾。
dbo.CDSUnvalidatedData 沒有這一欄：來源的 CDS 只寫不改，儀器讀值不會被作廢。

水位線請用「已讀到的最大 storeTime」，並用 > 而不是 >=。 同一秒內可能有多列，ORDER BY 再帶上識別鍵的欄位可確保順序穩定。

補撈的資料可能落在水位線後面。storeTime 是來源的時間戳， 醫院端補撈歷史資料時會寫進一批 storeTime 很舊的列，貴司的水位線早就越過那個點了， 那一批不會被增量查詢讀到。醫院端補撈後會通知，屆時請把該段時間範圍整段重讀 （WHERE storeTime BETWEEN @from AND @to）。

重複與版本：醫院端怎麼處理

資料表識別鍵同一組識別鍵再次出現時
CDSUnvalidatedData lifetimeNumber + terseLabel + propName + chartTime 不會再寫一列。來源的 CDS 只寫不改，同一筆量測的內容不會變， 時間窗重疊而重複撈到的部分在寫入前就被擋掉了。一組識別鍵永遠只有一列。
CISData 病人識別欄位（醫院端內部使用）+ interventionId + chartTime 內容一模一樣就不寫；內容真的變了（護理師改過、或被作廢）就 多一列，舊的那一列原封不動留著。一組識別鍵可能有多列， 以 storeTime 分先後。
05

需要預期的情況

以下都是正常運作下會出現的狀況，請勿視為資料錯誤。

情況表上的表現建議處理
該時段確實沒有資料 那段時間沒有新的列 正常，這不是故障
病人資料暫時查不到 那一輪的量測整列不寫入，表上就是少了那段時間的資料 約定是認不出是誰的資料不進表——沒有病歷號的列不會出現，也不會用床號代替。 病人對應恢復之後的輪次會照常寫入，但中斷期間的量測不會回頭補（環狀表只留約 26 小時）
項目標籤尚未建檔 terseLabel 為 NULL，interventionId 正常 保留原始值並回報醫院端補上對照，不要丟棄整列
部分加護單位查詢失敗 該單位的病人這一輪沒有新列，其餘照常寫入 缺漏會在後續輪次補回，不必特別處理
紀錄被護理師修改 dbo.CISData 多一列：同樣識別鍵、storeTime 更新， 舊的那一列原封不動留著 取同一組識別鍵裡 storeTime 最大的那一列當現值，見 §4 的範例 SQL
紀錄在 ICCA 被刪除或作廢 dbo.CISData 多一列：同樣識別鍵、isDeleted = 1、 storeTime 更新；原本 isDeleted = 0 的列留著 一樣取最新那一列，看它的 isDeleted 決定要不要把自己那一份標成作廢； 不要在增量查詢裡就過濾掉 isDeleted = 1
醫院端補撈歷史資料 寫進一批 storeTime 很舊的列，落在貴司水位線後面 這批不會被增量查詢讀到。醫院端補撈後會通知，請把該段時間範圍整段重讀 （WHERE storeTime BETWEEN @from AND @to），見 §4
整段時間完全沒有新列 醫院端可能已經斷線，也可能真的沒資料——表上分不出來 醫院端有服務日誌與落後告警，會主動處理。貴司若要自行核對，用 SELECT DATEDIFF(MINUTE, MAX(insertedAt), SYSDATETIME()) FROM dbo.CDSUnvalidatedData， 超過 15 分鐘即為異常
06

需要確認的事項

主機、資料庫的建置、寫入與維運都在醫院端——專用 Server 已於 2026-08-06 與資訊室主任的會議中確認由醫院端提供， 廠商不需要準備硬體。以下三項確認後即可開通；時間格式已定案，見 §1。

Q1

取用方式與帳號

要開唯讀帳號直接查表、還是走醫院端提供的 API，由醫院端決定。

採 API 時，token 由醫院端核發， 可取用的資料範圍在醫院端依 token 篩選後才回傳

Q2

資料要保留多久

每天約 50 萬列。醫院端會依貴司需要的期限設定清理排程（例如「保留 7 天」）。

若貴司會把資料完整複製一份到自己的系統，這裡可以設得短一些 （例如3天），中介庫就只當緩衝用。

Q3

表結構確認

請確認可接受 §2、§3 的表名、欄位名稱與型別。若貴司已有既定的命名慣例， 現在調整成本最低；一旦開始寫入就要考慮既有資料的搬移。
