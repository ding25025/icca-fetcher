整合流程 · 直接寫資料庫

一支常駐服務，兩個排程，資料直接落到中介資料庫

icca-fetcher 自己定時撈，撈完把 records[] 攤平成一筆一列， 只新增地寫進中介資料庫的兩張表。中間沒有 JSON 檔、沒有轉格式、沒有整合引擎。 已經寫進去的列不會再被改動也不會被刪——護理師改過的紀錄是多寫一列。 下游從那兩張表讀，交接點就是表結構——完整規格見 中介資料庫 Schema。

服務 127.0.0.1:8770 寫入 ICU_DW · CDSUnvalidatedData / CISData 狀態 待接正式機 作者 Vicky Wu

排程佈局

同一個 5 分鐘節奏，兩邊同時撈

兩邊都是每 5 分鐘同時觸發，但來源與欄位完全不同，各自跑各自的交易——一邊失敗不影響另一邊。 形狀一樣：時間到 → 撈 → 攤平 → 寫入。 設定就是 sink.schedule 裡的兩個數字（現在都是 5）。

排程 A

生命徵象

每 5 分鐘 · 寫進 CDSUnvalidatedData
  1. Timer

    服務內建排程

    "schedule": { "vitalsMinutes": 5 }

    上一輪還沒跑完就跳過這一輪，不排隊。

  2. vitals.js

    撈近 6 分鐘

    間隔 + 1 分鐘餘裕。溫熱的連線池平行查 7 個 CDS，先定位環狀表的寫入頭。

  3. sink.js

    攤平成一筆一列

    records[] 展開，病歷號跟著每一列走（床號不寫進表）。時間走字面值，不會被驅動再換算一次。

  4. SQL Server

    一個交易 INSERT 進去

    #stage → 濾掉已經有的 → INSERT dbo.CDSUnvalidatedData

    唯一鍵是病歷號＋terseLabel＋propName＋chartTime。 已經在表裡的那幾列就不寫，出錯整批 rollback。

排程 B

神經評估

每 5 分鐘 · 寫進 CISData
  1. Timer

    服務內建排程

    "schedule": { "neuroMinutes": 5 }

    跟生命徵象同時觸發，護理師剛填完幾分鐘內就會進表。

  2. neuro.js

    撈近 6 分鐘

    照 HostDb 分片平行查各 charting 資料庫。正式機實測整輪約 0.9 秒。

  3. sink.js

    攤平成一筆一列

    同一套程式，只是欄位不同。病人的鑰匙用 ptEncounterId，不受轉床影響。

  4. SQL Server

    一個交易 INSERT 進去

    #stage → 比對內容 → INSERT dbo.CISData

    內容一模一樣就不寫；護理師改過或作廢就多一列，舊的那一列原封不動留著。

單次觸發 · 時序

一個 5 分鐘週期實際發生什麼

編號就是先後順序。撈的那幾步是既有的 vitals.js，一行都沒改； 改的只有最後：結果不再變成檔案或 HTTP 回應，而是直接進資料庫。

01 排程

服務內建的計時器到點。

上一輪還沒結束就跳過，log 寫一行警告——排隊只會越積越多，而下一輪的窗本來就蓋得到漏掉的那一段。

02 vitals.js

用溫熱的連線池平行查 7 個 CDS：先定位環狀表的寫入頭，只查該撈的那一兩張。

同時向 primary 查在床病人，兩邊用床號對起來。

03 vitals.js

合併、去重、換算成本地時間，依床號自然排序，得到一床一筆的結果。

04 sink.js

records[] 攤平成一筆一列，鑰匙欄位的 null 正規化成空字串（HR 這種單值項目的 propName 就是 ''）。

SQL Server 的 NULL 不等於 NULL——鑰匙留著 null 的話比對永遠比不中，每一輪都會多寫一列。

05 sink.js

開交易 → 建 #stage → 分批 INSERT（一批約 200 列）→ 跟正式表比對、把新的一次 INSERT 進去 → commit。

分批是因為 SQL Server 單次請求最多 2100 個參數。整段在同一個交易裡，中途失敗全部 rollback。

06 log

寫一行結果：這一輪撈到幾筆、實際寫進去幾筆、重複略過幾筆、花了多久。

07 失敗

撈失敗或寫失敗都只寫 log，服務照常活著、下一輪再試。全部站台掛掉的那一輪不寫——0 筆寫進去跟「真的沒資料」長得一模一樣。

參數對齊

時間窗要跟排程間隔對齊

window 是「撈最近幾分鐘」。窗比間隔小會漏資料，比間隔大則會重複撈到—— 但重複的那一份在寫入前就被擋掉了。兩種風險不對等，所以一律往重疊的那邊倒。

Route 觸發間隔 建議 window 結果
A 生命徵象 5 分鐘 6 多 1 分鐘重疊，排程晚一點也不會斷片
B 神經評估 5 分鐘 6 同上。重疊的部分內容沒變就不會寫進去
補撈 臨時 30 / 1440 某輪掛掉就 GET /icca/push/vitals?window=30 把窗開大再打一次
心跳 1–5 分鐘 — 打 /health，再加一句 MAX(insertedAt) 查詢盯資料本身，落後超過 15 分鐘就是異常

失敗怎麼表達

「沒資料」和「壞掉」不能長得一樣

寫進資料庫之後這件事更重要了：下游看到的是表，表裡沒有新資料的時候， 它分不出是這段時間真的沒量測，還是撈的那一端已經斷了三個小時。

全滅 · 不寫

所有站台都連不上

這一輪不寫任何東西，log 留下各站的失敗原因。寫 0 筆進去跟「真的沒資料」在表裡 完全一樣，等有人發現已經斷好幾小時了。

部分失敗 · 照寫

有幾站掛了，其餘照寫

剩下的資料還是有用，照樣寫進去，log 寫一行警告。哪幾床沒進來要對照 /icca/vitals?withSummary=1 才看得出來。

寫 0 筆 · 正常

撈到了，但全是重複的

時間窗重疊時本來就會這樣，written 接近 0 正代表去重是通的。 跟「撈不到」是兩件事，log 裡分得出來。

寫入失敗 · rollback

中介資料庫連不上或被鎖住

整批 rollback，不會留半批。服務照常活著、下一輪再試；補的方法是把 window 開大再打一次 /icca/push/*。

已定案 · 只新增不更新

鑰匙就是資料表設計的核心

時間窗一定會重疊，同一筆資料至少被撈到兩次。重複的在寫入那一刻就擋掉， 下游不必再約定「誰負責去重」。但只擋一模一樣的——內容真的變了是多寫一列， 既有的列一律不動。

CDSUnvalidatedData

病歷號 ＋ terseLabel ＋ propName ＋ chartTime

CDS 那邊只有床與儀器，但床號不寫進中介表——同一床會換病人。撈的時候用床號 對到病歷號，對不到的整列不寫。terseLabel 要配 propName—— ABP 底下有 systolic / diastolic / mean 三種，只看前者分不出是收縮壓。 量測時間對外叫 chartTime（ICCA 端是 measurementTime）， 跟 CISData 的臨床時間同名同角色。

CISData

ptEncounterId ＋ interventionId ＋ chartTime

鑰匙這裡不能用病歷號：同一位病人的病歷號在紀錄被改寫時不保證跟著走， ptEncounterId 則是從入院到出院都不變。病歷號仍然一律要有值， 沒有就整列不寫。ptEncounterId 不在 JSON 輸出裡，程式內部一直有，寫入時才拿出來用； 對外規格也不公開這一欄，只說「醫院端內部使用的病人識別欄位」。

比中之後

兩張表都不做 UPDATE

儀器讀值不會改，比中就不寫，一組唯一鍵永遠只有一列；primary 掛掉查不到病歷號的那一輪 整批不寫，不會留下認不出是誰的列。病歷紀錄則是護理師可以回頭改的—— 改過或作廢（isDeleted = 1）都是再寫一列，同一組識別鍵底下靠 storeTime 分先後，最大的那一列是現值。CDSUnvalidatedData 沒有 isDeleted，來源只寫不改。

下游怎麼讀

用 storeTime 當水位線

表只會長大不會清，下游要增量讀就查 storeTime > @上次——它是 ICCA 端的寫入時間， 紀錄被改時會跟著變新，所以新資料與新版本都追得到。表裡沒有流水號欄位，也沒有 updatedAt／changedAt：列寫進去就不會再動，那兩欄沒有值可以放。 insertedAt 留著，但只拿來核對拋轉有沒有斷（同一批寫入的時間戳相同，當水位線會重複讀或漏讀）。 補撈歷史資料寫進去的列 storeTime 很舊，會落在下游水位線後面讀不到——補完要通知下游把該段整段重讀。

量體

一天約 50 萬列

生命徵象一輪約 1800 筆、288 輪，加上神經評估。走的是內網 SQL 連線， 一輪的寫入時間以秒計。清理排程也是院方要做的事——庫是院方的， 沒有別人會來收，期限一天沒定表就一天在長。

排錯 · 落檔

手動跑，產 JSON 檔

node vitals.js --no-db 照舊寫出 vitals_{ts}.json， 用來確認欄位與內容。設 alsoWriteFile 則是寫資料庫的同時也留一份。

正式 · 寫資料庫

服務常駐，自己定時寫

同一段程式，撈完直接進表。沒有中間格式、沒有整合引擎、沒有訊息佇列—— 少三個可能斷掉的地方。

部署

nssm 註冊成 Windows 服務，不掛 IIS

server.js 自己就是 HTTP server，前面不需要再放一層。IIS 的 application pool 會 idle 回收行程，正好把常駐連線池與表號快取打掉——那是這支服務唯一的優點。 用 nssm 開機自動啟動、當掉自動重拉；改設定檔要 restart 才會重讀。

建表

庫是院方的，所以建表很自由

不必跟外部單位協調 DDL：node sink.js --init 直接建，或把 sql/sink-schema.sql 交給院內 DBA 建好再把 ensureTables 關掉。 node sink.js --check 看得到通不通、表在不在、目前幾筆。

還沒定的事

接正式機之前要先確認

  • 中介資料庫的連線資訊——8/6 與資訊室主任會議討論確認，由院方提供一台專用 Server，庫也由院方建置維護，所以主機與權限都不是問題（要 CREATE TABLE 讓 ensureTables 自己建也行）。還缺的是實例名稱、資料庫名稱、寫入帳號與備份策略。
  • 下游的唯讀帳號要開給誰——來源 IP／網段、幾組帳號，只給那兩張表的 SELECT。要不要另開一組測試庫的也一起決定。
  • 表名與欄位要不要改——目前是 CDSUnvalidatedData / CISData，欄位沿用撈出來的原名。下游若已經有既定的命名慣例，現在改最便宜（改 sink.js 的 spec，重新產一次 DDL）。
  • 舊資料保留多久——一天約 50 萬列，清理由院方排程做，但期限要看下游要不要自己留一份：下游會完整複製走的話這裡設短一點（3 天）就夠，中介庫只當緩衝；不複製的話至少 7 天。規格書 §6 Q2 已經把這題丟給下游回答。
