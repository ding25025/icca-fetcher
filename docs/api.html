ICCA Fetcher API

ICCA CDS、Primary 與 Charting DB 的內部擷取與中介庫同步服務。

快速開始

在專案根目錄設定好 databases.config.json 與 sink.config.json 後啟動：

node server.js
# 預設：http://127.0.0.1:8770

先確認服務狀態：

curl http://127.0.0.1:8770/health
此服務設計為內部使用。預設只綁定 127.0.0.1；若改為其他主機可連線，建議設定 ICCA_TOKEN。

端點總覽

端點用途是否寫入中介庫
/health服務狀態、同步水位與補撈建議；寫入過期或失敗時回 503否
/icca/vitals取得生命徵象 JSON否
/icca/neuro取得神經／Charting 紀錄 JSON否
/icca/push/vitals擷取各 CDS 站並寫入中介庫是
/icca/push/neuro擷取各 Charting DB 並寫入中介庫是
/icca/head目前 CDS 環狀表 head否
/icca/order26 張 CDS 輪替表的新舊順序否
/icca/latest跨表取得最新原始資料否
/icca/at定位指定時間所在表；可順便取得資料否

生命徵象

GET /icca/vitals

回傳一床一筆，每床的量測值位於 records[]。不寫入中介庫。

GET /icca/push/vitals

逐 CDS 站擷取並寫入中介庫。每站獨立成功／失敗與水位。

curl "http://127.0.0.1:8770/icca/vitals?window=15&site=cds1,cds2&withSummary=1"
curl "http://127.0.0.1:8770/icca/push/vitals?window=30"
curl "http://127.0.0.1:8770/icca/push/vitals?site=cds2&window=139"
參數說明
window 或 w最近幾分鐘；讀取 API 預設上限 60 分鐘，push 預設上限 1,440 分鐘。
site指定 CDS 站台，可用逗號分隔，例如 cds1,cds2。
param指定 parameterId 清單。
utc=1時間保留 UTC；預設回傳台灣時區顯示時間。
withSummary=1回傳 { summary, rows }，包含每站成功或失敗資訊。
noPatients=1不查 Primary DB 病人資料。
keepUnmatched=1保留無法對應病歷號的床位。

神經與 Charting 紀錄

/icca/neuro 與 /icca/push/neuro 先從 Primary DB 找出在床病人與其 HostDb，再依實際的 Charting DB 分組查詢 PtIntervention。

curl "http://127.0.0.1:8770/icca/neuro?window=60&withSummary=1"
curl "http://127.0.0.1:8770/icca/push/neuro?window=180"
參數說明
window 或 w最近幾分鐘，最多 1,440 分鐘。
utc=1時間保留 UTC。
primaryDb指定 Primary 資料庫，主要用於排錯。
withSummary=1包含各 Charting DB 分片的查詢狀態。

健康檢查與監控

GET /health 不連資料庫、不需要 token，只讀本機的寫入紀錄。建議每 1～5 分鐘拉一次：

statusHTTP意義
ok200各種類都在門檻內，且沒有失敗紀錄。
starting200剛啟動、還沒有成功紀錄，仍在寬限期（預設 2 分鐘）。可稍後重查。
degraded503寫入失敗或資料過期，應告警並查 reasons；不要拿它當自動重啟的條件。

原有的 lastWrite 不變，另外新增 checks.vitals 與 checks.neuro：

{
  "status": "degraded",
  "checks": {
    "vitals": { "status": "degraded", "staleMinutes": 15,
                "reasons": ["stale", "write_failed"], "failedSources": ["cds2"] },
    "neuro":  { "status": "ok", "staleMinutes": 15, "reasons": [], "failedSources": [] }
  },
  "lastWrite": { }
}
reasons意義
write_failed整輪或某個來源上一次寫入失敗。
stale最舊的來源超過 staleMinutes 沒有成功寫入。
no_success超過寬限期仍沒有任何成功紀錄（常見於排程從未執行）。
gap_beyond_backfill缺口已超過補撈上限，補撈補不回來，需要人工處理。

有內建排程的種類會自動納入監控，門檻預設為排程間隔的三倍（每 5 分鐘跑一次即 15 分鐘）。用外部排程器時請自己填門檻，否則第一次寫入之前偵測不到「排程從未執行」。/health 只證明本機有沒有成功寫入，不能證明來源端仍在產生新資料。

併發與逾時

工作分成 vitals、neuro 與各站台的 ring:<站台名稱>，每組同時只跑一輪；讀取與 push 共用同一組名額。ring 四個診斷端點在同一站台共用一組，不同站台可以並行；省略 site 或大小寫不同但指向同一站，仍算同一組。/health 不排隊。內建排程也共用名額，但忙碌時直接跳過、不排隊。

  • 同組已有一輪在跑時，後來的請求會排隊（預設最多 2 筆、等待上限 30 秒）。
  • 隊伍已滿或等待逾時回 503，附 Retry-After: 30。請照這個秒數退避，不要立刻重送。
  • 開始執行後整輪期限預設 180 秒，超過回 504，服務會要求取消該輪 SQL、阻止後續查詢與交易提交。
  • 504 不代表完全沒寫入：已完成的來源不會撤回，補撈前先查 /health。
  • 呼叫端的 timeout 應大於「等待上限 + 整輪期限」（預設合計 210 秒）。

同步結果與補資料

push 回應的 sources[] 是逐來源結果。ok: false 不會推進該來源水位；其餘來源仍可正常寫入。

{
  "kind": "vitals", "fetched": 1820, "written": 1780,
  "sources": [
    { "source": "cds1", "ok": true, "written": 1180 },
    { "source": "cds2", "ok": false, "stage": "fetch", "error": "connect ETIMEDOUT" }
  ]
}

遇到失敗先查 /health?pretty=1，取該來源的 suggestWindowMinutes。CDS 可指定站台補撈：

curl "http://127.0.0.1:8770/health?pretty=1"
curl "http://127.0.0.1:8770/icca/push/vitals?site=cds2&window=139"

CDS 環狀表診斷

curl "http://127.0.0.1:8770/icca/head?site=cds1"
curl "http://127.0.0.1:8770/icca/order?site=cds1"
curl "http://127.0.0.1:8770/icca/latest?site=cds1&n=100&param=4102"
curl "http://127.0.0.1:8770/icca/at?site=cds1&at=2026-09-02%2010:00&fetch=1&n=100"
參數適用端點與說明
site所有 ring 端點；指定 CDS 站。
nlatest、at&fetch=1；預設上限 1,000 筆。
param、patient、device篩選原始資料。
from、to依量測時間篩選。
at、by=store|measure、fetch=1定位時間點；加 fetch 同時取回該表附近資料。

回應與錯誤

HTTP 狀態意義
200成功；部分來源失敗時也會是 200，請看 summary 或 sources[]。
400參數不合法、超過 API 上限，或 sink 未啟用。
401設定 token 時未提供或 token 不正確。
502所有來源都失敗，或全部來源都無法寫入中介庫。
503同組工作忙碌或排隊逾時（附 Retry-After: 30）；ring 端點無法取得資料庫連線；/health 判定為 degraded。
504整輪執行超過 jobTimeoutMs，已要求取消查詢。可能已有部分來源寫入，先查 /health 再決定補撈。

設定與限制

可在 databases.config.json 的 server 區塊調整 API 上限：

{
  "server": {
    "maxVitalsWindowMinutes": 60,
    "maxNeuroWindowMinutes": 1440,
    "maxPushWindowMinutes": 1440,
    "maxLatestRows": 1000,
    "maxAtRows": 1000,

    "accessLog": false,
    "maxQueuedRequests": 2,
    "queueTimeoutMs": 30000,
    "jobTimeoutMs": 180000,

    "health": {
      "startupGraceMinutes": 2,
      "staleMinutes": { "vitals": 15, "neuro": 15 }
    }
  }
}
設定預設說明
accessLogtrue設 false 只留錯誤 log，避免高頻輪詢洗版。
maxQueuedRequests2每組最多幾筆排隊（不含執行中那筆）；0 表示忙碌即拒絕，上限 100。
queueTimeoutMs30000排隊等待上限，上限 600000。
jobTimeoutMs180000整輪期限，含撈取與寫入，上限 3600000。大範圍手動補撈前可調高。
health.startupGraceMinutes2啟動後多久之內沒有成功紀錄仍算 starting。
health.staleMinutes.<種類>排程間隔 ×3新鮮度門檻（分鐘）；設 false 可把只手動跑的種類排除監控。

以上設定修改後需重啟服務才會生效。

時間窗上限仍不會超過 ICCA_MAX_BACKFILL_HOURS（預設 24 小時），ring 單次筆數硬上限為 5,000。完整操作細節請見 SERVER.md。
