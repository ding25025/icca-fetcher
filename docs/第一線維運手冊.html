第一線支援用

ICCA 資料擷取服務

第一線維運手冊｜不需要程式背景

請勿修改程式碼或設定檔。除非維護人員指示，請不要修改 databases.config.json、sink.config.json，也不要刪除 .sink-state.json。

正常情況

  • http://127.0.0.1:8770/health 可開啟，且有 "status":"ok"。
  • checks 裡 vitals 與 neuro 都是 "status": "ok"，reasons 是空的。
  • lastWrite 中 vitals 與 neuro 的最後成功時間持續更新。
  • 中介資料庫資料時間通常不落後目前時間超過兩到三個排程間隔（一般為 5 分鐘）。

每日檢查（約 1 分鐘）

  1. 在服務主機開啟瀏覽器，輸入：
    http://127.0.0.1:8770/health?pretty=1
  2. 確認最上方為 "status": "ok"。
    • "starting"：服務剛啟動、還沒寫第一輪，等 5 分鐘再看一次。
    • "degraded"（網頁可能顯示錯誤或 503）：依下方「資料沒有更新」處理。
  3. 查看 checks 與 lastWrite。若 vitals 或 neuro 顯示失敗、時間很久以前，依下方處理。

常見問題處理

服務無法開啟／health 網址連不上

  1. 確認是在服務主機上開啟網址，且網址是 127.0.0.1:8770。
  2. 以系統管理員身分開啟 CMD，執行：
    nssm status ICCA-Server
  3. 若不是 SERVICE_RUNNING，執行一次：
    nssm restart ICCA-Server
  4. 等待 1 分鐘後再次開啟 health 網址。
  5. 仍失敗時，截圖並收集錯誤 log；不要反覆重啟。

health 顯示 degraded，或資料沒有更新

  1. 重新整理 health 網址，記下異常類型：vitals 或 neuro。
  2. 看該類 checks 裡的 reasons：
    • write_failed：寫入失敗，看 failedSources 是哪個來源。
    • stale：太久沒有新資料進來。
    • no_success：從開機到現在一次都沒成功，多半是排程沒跑或設定有問題。
    • gap_beyond_backfill：缺口已經太大，補撈補不回來，直接回報維護人員。
  3. 查看 lastWrite 裡的 lastError、failedSources 或錯誤文字。
  4. 可安全重啟服務一次：
    nssm restart ICCA-Server
  5. 等待 5～10 分鐘後再查看 health。
  6. 仍未更新時交由資訊室／DBA／程式維護人員。不要自行大量補撈資料。

Log 出現紅字、✗、500、502、503 或 504

  • fetch：常見為來源資料庫、權限、網路或查詢問題，聯絡資料庫／網路管理人員。
  • sink：資料已撈到但不能寫入中介資料庫，聯絡中介資料庫 DBA。
  • group：資料對應異常，交給程式維護人員。
  • 500／502：截圖完整錯誤文字；可重啟一次，持續出現就停止重試並回報。
  • 503（工作忙碌／排隊逾時）：上一輪還沒跑完。等 30 秒以上再看，偶爾出現是正常的；一直出現才回報。不要連續重送。
  • 504（整輪執行逾時）：這一輪被中止，但可能已經寫進一部分資料。不要立刻自行補撈，先看 health 再交給維護人員。

Node.js 記憶體偏高

約 100～200 MB 通常正常。請看趨勢：整天大致穩定即正常；若每輪都明顯增加、持續達數百 MB 或數 GB，截圖工作管理員，重啟一次後回報維護人員。

如何查看 log

若服務以 NSSM 安裝，預設位置：

logs\server.out.log
logs\server.err.log

優先看最新幾行，記下發生時間、錯誤文字、vitals/neuro 與來源名稱。不要直接寄出完整 log，內容可能含內部主機名稱或病人相關資訊。

可做與不可做

可以做不要做
查看 health、log、Windows 工作管理員修改資料庫密碼、連線位址或 SQL 檔
確認異常後重啟服務一次反覆重啟、連續重送忙碌（503）的請求，或同時開多個 node server.js
擷取錯誤畫面並回報刪除 .sink-state.json 或中介資料表
記錄異常開始與恢復時間在正式環境執行大範圍補撈

交接給第二線時，請提供

  1. 問題開始、發現與恢復時間。
  2. health 畫面／內容（含 status 與 checks，遮蔽病人資訊）。
  3. nssm status ICCA-Server 的結果。
  4. 最近一次重啟時間，以及是否改善。
  5. server.err.log 最新錯誤的時間與完整訊息。
  6. 影響範圍：vitals、neuro，或特定來源／病房。

維護人員提醒

  • 修改設定檔後，必須執行 nssm restart ICCA-Server 才會重新讀取。
  • 密碼應以 env:環境變數名稱 管理，請勿放在設定檔明文或截圖中。
  • 需補資料時，先確認 health 回傳的建議範圍，再由熟悉資料庫的人員執行。
